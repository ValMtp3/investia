# Spec 23c — A2UI 1.0 en complément d'AG-UI (P9.4)

> Chantier 23c, issu de la veille OSS du 15/11/2026 (D94) : **A2UI 1.0** (Google,
> annoncé 11/11/2026, Apache-2.0, spec v1.0 sur a2ui.org + github.com/a2ui-project/a2ui)
> est le nouveau protocole agent→UI déclaratif de novembre 2026. L'agent envoie des
> messages JSON décrivant l'UI (`surfaceUpdate` = composants {id, type, props, childIds},
> `dataModelUpdate` = data-binding, `beginRendering` = {surfaceId, root, catalogId},
> `deleteSurface`) ; le **client rend avec son propre catalogue de composants** —
> exactement notre modèle de whitelist 21b, mais standardisé.
>
> On a déjà : AG-UI 1.0 (21a état partagé, 21b generative UI `ui_component` whitelist
> double côté) sur `protocol=agui`. **A2UI vient en complément, pas en remplacement** :
> nouveau `protocol=a2ui` sur la même route SSE, legacy et agui inchangés.

## Objectif

Exposer nos composants génératifs (pour l'instant `HistoryChart` via `get_history`)
en **A2UI 1.0**, avec la même sécurité que 21b (whitelist double, validation stricte,
jamais de HTML brut).

## Contrat détaillé

### 1. Backend — nouveau `agent/a2ui.py`

- `A2UI_CATALOG_ID = "investia-v1"` ; whitelist serveur `A2UI_COMPONENT_BY_TOOL`
  (même contenu que 21b : `get_history` → composant `HistoryChart`, props littérales
  `{symbol, days}` dérivées des arguments de l'outil, types bornés).
- `to_a2ui_messages(kind, payload) -> list[dict]` :
  - `start` → `[{"version": "1.0"}, {"deleteSurface": {"surfaceId": ...}}]` pour les
    surfaces du run précédent (state côté sink, comme RunStateAccumulator) ;
  - `tool_call` d'un outil whitelisté → `surfaceUpdate` (surfaceId = `ui-<tool_call_id>`,
    components = [root {id, type: nom du catalogue, props littérales}]) + `beginRendering`
    ({surfaceId, root, catalogId}) ;
  - autres kinds → `[]` (A2UI ne transporte que l'UI ; le texte/les steps restent en
    AG-UI/legacy — un client A2UI pur n'est pas la cible de ce chantier).
- Validation pydantic stricte avant émission : type de message ∈ {version, surfaceUpdate,
  dataModelUpdate, beginRendering, deleteSurface} ; composant ∈ whitelist ; props =
  littéraux JSON uniquement (str/int/float/bool), jamais de HTML/DSL/macros A2UI.
- `format_a2ui_sse(kind, payload, state=None) -> str` : blocs `data: {json}\n\n`.

### 2. Route — `protocol=a2ui` sur `POST /agent/run`

- `protocol: Literal["legacy", "agui", "a2ui"] = "legacy"` ; `a2ui` → le sink formate en
  A2UI (pas de StateSnapshotEvent, spécifique AG-UI). `legacy`/`agui` inchangés.
- `/api/agents/run` : idem si le câblage est identique (mêmes sink), sinon hors périmètre.

### 3. Frontend — `dashboard/src/a2ui.ts` + `A2UISurface.tsx`

- Parse les blocs SSE A2UI → maintient un modèle `Map<surfaceId, {root, components, dataModel}>`
  (apply surfaceUpdate/dataModelUpdate/beginRendering/deleteSurface).
- Catalogue client `A2UI_CATALOG: Record<string, ComponentType>` (whitelist) — réutilise
  `HistoryChart` de 21b ; composant inconnu ou props invalides → ignoré (rendu d'un
  placeholder neutre), jamais d'erreur fatale.
- `A2UISurface` rend l'arbre (root + childIds) depuis le catalogue.
- Page Agent : `?protocol=a2ui` branche ce flux (à côté de legacy/agui).

### 4. Sécurité (héritée de 21b, renforcée)

- Whitelist **double** (serveur `A2UI_COMPONENT_BY_TOOL` + client `A2UI_CATALOG`).
- Validation pydantic serveur des messages ; props littérales JSON uniquement.
- Pas de rendu HTML/MDX brut ; pas de macros/DSL Express A2UI (non supportés, documenté).
- Pas d ações utilisateur (userAction) en v1 — le serveur n'attend pas d'action client.

## Critères d'acceptation

- Suite non-integration verte, ruff/format/ty propres, dashboard tests/lint/build verts, CI verte.
- `protocol=a2ui` émet des messages A2UI valides ; le dashboard rend `HistoryChart` via le
  catalogue whitelist ; composant inconnu ignoré des deux côtés.
- legacy et agui inchangés (tests existants verts).

## Hors périmètre

- Data-binding serveur avec les vraies séries (v1 = props littérales, le client fetch comme 21b).
- Actions utilisateur bidirectionnelles (userAction) et composants interactifs (Confirmation).
- Express DSL / Macros A2UI (code dans les messages → jamais exécuté chez nous).
- MCP Apps (ext-apps) en iframe, pont @ag-ui/a2ui-middleware (on émet A2UI nativement).
- A2A 1.1 AI Catalog, ACP — autres chantiers.
